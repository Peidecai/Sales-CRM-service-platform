# ASR 本地部署 vs API 费用对比分析（面向 CRM 通话录音）

## 1. 结论先行

对于本项目（`recordings -> ASR -> call_transcripts -> AI分析`）：

- 低调用量阶段（POC / 早期上线）通常 `API` 成本更低，主要因为人力和运维开销更少。
- 中高调用量阶段（业务稳定、录音时长持续增长）通常 `本地部署 SenseVoiceSmall` 更有成本优势。
- 最稳妥方案是 `混合架构`：主链路本地 ASR，失败或峰值时回落 API。

---

## 2. 项目场景与成本边界

本项目的 AI 推理涉及两类能力：

- **ASR 语音转写**：录音上传后异步入队转写（Bull 队列）。
- **LLM 分析**：基于转写文本做摘要/分类/评分（当前是 DashScope 兼容接口）。

本文仅比较 **ASR 层** 的费用模型（SenseVoiceSmall 本地 vs 云 ASR API）。  
LLM 分析费用应单独核算。

---

## 3. 两种成本模型定义

### 3.1 本地部署（SenseVoiceSmall）

月总成本：

`C_local = C_gpu + C_cpu_mem + C_storage + C_bandwidth + C_ops + C_amortization + C_risk`

说明：

- `C_gpu`：GPU 服务器租用或折旧 + 电费
- `C_cpu_mem`：CPU/内存基础资源
- `C_storage`：音频与日志存储
- `C_bandwidth`：外网流量（若内网可近似为 0）
- `C_ops`：运维与值班人力（月度人天折算）
- `C_amortization`：开发接入和模型服务化成本摊销
- `C_risk`：可用性风险预留（可按 5%~15%估算）

单小时音频成本：

`U_local = C_local / H_month`

其中 `H_month` 为当月总转写时长（小时）。

### 3.2 云 API（按量计费）

月总成本：

`C_api = H_month * P_api + N_req * P_req + C_egress + C_fallback`

说明：

- `P_api`：每小时音频价格（或按分钟换算）
- `N_req`：请求次数
- `P_req`：单次请求附加费用（若有）
- `C_egress`：回传流量与公网费用
- `C_fallback`：重试、失败补偿、双写等额外开销

单小时音频成本：

`U_api = C_api / H_month`

## 5. 盈亏平衡点（Break-even）

当 `C_local <= C_api` 时，本地部署更划算。  
将 API 单价视作主变量可得：

`H_break_even = C_local / P_api_effective`

其中 `P_api_effective` 是把请求附加费、流量费折算后的“有效每小时价格”。

解释：

- 如果真实 `H_month > H_break_even`，优先考虑本地部署。
- 如果真实 `H_month < H_break_even`，优先考虑 API。

## 5.1 本地部署显卡与算力估算

### 5.1.1 显卡类型（必须）

SenseVoice 官方推理示例使用 `cuda:0`（即 NVIDIA CUDA 设备），因此部署侧至少需要：

- `NVIDIA` 显卡 + `CUDA` 环境
- 使用 Docker/FastAPI 封装时可以通过环境变量指定设备，例如 `SENSEVOICE_DEVICE=cuda:0` 或 `SENSEVOICE_DEVICE=cpu`

> 官方 README 没有给出“必须多少显存（VRAM）”的硬性数值；因此显存规划建议以“模型能稳定加载且不 OOM”为最终验收标准，并用与你们的输入音频时长分布做压测。

### 5.1.2 显存与选型建议（经验值）

- 入门：建议准备 `>= 12GB VRAM` 起步（用于服务化 + 基本并发测试）
- 推荐：`16GB VRAM` 级别更稳，便于做 batch / 排队缓冲
- 若追求更高并发（更大的 batch、或更长时长音频同时处理）：可以考虑 `24GB/48GB VRAM` 级别

最终以“你们实际推理程序的显存占用 + 压测成功率”来确定。

### 5.1.3 算力如何估算（用吞吐指标反推）

SenseVoice README 给出关键吞吐指标：`10s` 音频推理约 `70ms`。

因此可以计算实时因子（RTF，越小越快）：

- `RTF = T / L = 0.07s / 10s = 0.007`

换算得到单卡理论吞吐（“处理的音频秒数 / 墙上秒数”）：

- `audio_seconds_per_wall_second = 1 / RTF ≈ 142.9x`

在理想化假设下，如果平均每路音频时长是 `L_avg`（秒），粗估理论并发路数：

- `concurrency_theory ≈ 142.9 / L_avg`

直觉示例（仅用于估算数量级）：

- `L_avg = 10s`：并发约 `~14 路`
- `L_avg = 60s`：并发约 `~2~3 路`

注意：

- 真实并发会受 `VAD 切分/合并`、`batch_size_s`、GPU 调度、CPU 预处理、以及网络/OSS 拉取延迟影响。
- 你们项目是 Bull 异步队列，更建议用压测获得 `end-to-end latency`（包括 VAD + SenseVoice 总耗时），再映射到队列堆积与 SLA。

### 5.1.4 与你们 NestJS 队列的落点

你们现有链路是 `recordings -> asr(队列) -> call_transcripts -> call-analysis(LLM)`，因此本地部署建议把 SenseVoice 作为独立 ASR 微服务：

- `ASR 微服务`：FastAPI/HTTP（或 gRPC）
- `NestJS provider adapter`：负责音频取回、提交/轮询任务、把分段结果落库到 `call_transcripts`

这样你可以通过调参（`batch_size_s`、`merge_vad`、`max_single_segment_time` 等）把“吞吐/延迟”对齐到业务目标。

## 7. 非费用维度（决策必须项）

仅看成本会失真，建议并行评估：

- **数据合规**：通话录音是否允许离开私域网络。
- **稳定性**：API 供应商抖动与限流风险 vs 本地服务可用性风险。
- **可控性**：本地模型可调参、可扩展；API 受供应商策略影响。
- **迭代效率**：API 上线快；本地需要建设监控、告警、灰度、回滚。
- **说话人能力**：当前项目结构依赖 speaker 字段，本地方案可能需额外说话人分离模块。

## 8. 面向本项目的建议架构

推荐采用 **混合双轨**：

1. 主通路：`SenseVoiceSmall` 本地 ASR 服务（HTTP/gRPC）。
2. 兜底通路：云 API（超时/失败重试、流量突刺时分流）。
3. 统一适配：在 `ASR_PROVIDER` 抽象下实现 `SenseVoiceAsrAdapter` 与 `CloudAsrAdapter`。
4. 路由策略：按队列积压、失败率、SLA 动态切换。

优点：

- 费用可控：高频流量走本地，降低长期账单。
- 业务稳定：本地异常时可回退 API，避免业务中断。

## 9. 实施与核算清单

### 9.1 一周内可完成

- 收集过去 30 天录音总时长、平均时长、峰值并发。
- 获取 2~3 家云 ASR 报价，统一换算到“每小时有效价格”。
- 估算本地部署资源：GPU 规格、可承载实时倍率、月成本。
- 跑一轮样本集：识别准确率（CER/WER）+ 平均延迟 + 失败率。

### 9.2 决策门槛建议

- 识别质量达到业务基线（例如关键词提取准确率不低于现网 API）。
- 端到端成功率达标（含上传、转写、落库、分析链路）。
- 月成本对比连续 2 个周期，确认本地方案存在稳定优势。

## 11. 当前建议结论（基于项目现状）

- 你们已经有完整 ASR 异步链路与 provider 抽象，技术上具备接入本地模型的条件。

## 12. 后期云呼叫平台/硬件话机/网络费用的综合核算（补充：通话产生的成本）

在本项目后期引入“云呼叫平台（好销云、云客、磐石云、卓销云、畅享通等）”或“硬件话机（4卡话机、斯普林克话机、卡尔话机、傲锋话机等多卡槽外呼设备）”，新增的成本不只在 ASR/LLM，还包括：

- 呼叫中心 SaaS 的“通话计费”（通常按通道/座席/月 + 按通话分钟/量）
- 硬件话机的 CAPEX/OPEX（设备采购/租赁 + SIM/运营商话费/维护）
- 网络与流量费用（通话录音文件的拉取/回传、OSS/存储之间的数据传输、公网出入流量）

下面给出一套可落地的“月度测算框架”，你只要把供应商报价/本地网络数据替换到占位符即可。

### 12.1 统一口径：用“月通话时长”做主变量

定义：

- `H_call_month`：月通话总时长（小时）
- `N_call_month`：月通话笔数（通话次数）
- `L_avg_call_min`：平均单次通话时长（分钟）

关系：

- `H_call_month = N_call_month * L_avg_call_min / 60`

### 12.2 云呼叫平台（SaaS）费用模型

云呼叫平台通常包含以下计费项（不同厂商可能拆分口径略有差异）：

- `P_channel_month`：通道/座席/月（或并发外呼能力/月）
- `P_minute`：按分钟计费（通话分钟/回拨分钟/IVR分钟等）
- `C_setup`：开通/配置/集成一次性费用（可摊到月度：`C_setup_month = C_setup / 期数`）
- `C_webhook_call`：Webhook/回调次数费用（若有）

月总成本（建议用“有效分钟”作为分钟口径）：

`C_saas = H_call_month * 60 * P_minute + N_channel * P_channel_month + C_setup_month + 其他项`

其中 `N_channel` 是你需要的通道/并发能力数量（可结合峰值并发外呼策略确定）。

### 12.3 硬件话机方案费用模型

硬件外呼设备通常包含：

- `C_device`：设备购买成本或租赁成本（建议按折旧摊到月度：`C_device_month = C_device / 设备寿命月数`）
- `C_slot_month`：多卡槽相关的管理成本（若需要额外硬件/网关/主机）
- `C_sim_month`：SIM/号码包/月租（或按号码数计费）
- `P_mobile_minute`：运营商话费（通常按通话分钟/目的地费率）
- `C_maint`：维护/更换/现场安装（可摊月度）

月总成本：

`C_hw = C_device_month + C_slot_month + N_number * C_sim_month + H_call_month * 60 * P_mobile_minute + C_maint`

备注：

- 硬件方案的单位分钟成本往往更“可控”，但更依赖运营商费率、地区、号码质量与维护效率。
- 若你们需要 4 卡、或多台多槽设备以覆盖峰值并发，`N_number` 与 `N_channel` 会同时增长，需要在测算表里联动填入。

### 12.4 网络费用模型（综合“ASR链路 + 呼叫录音链路”）

网络成本建议拆成两类：音频数据相关出入流量 + 业务 API/网页/WSS 的基础流量（后者通常较小，音频更关键）。

定义：

- `V_audio_gb_month`：月音频录音数据量（GB）（录音文件下载/回传/存储之间的传输合计）
- `P_egress`：公网出流/跨区域传输的单价（元/GB）（来自你的云商或运营商报价）
- `C_transfer_other`：其他网络相关费用（NAT、专线、SLB/Nginx等，若你们算进网络成本）

音频网络月成本：

`C_net_audio = V_audio_gb_month * P_egress + 其他传输项`

如何估算 `V_audio_gb_month`（可选其一）：

- 方法 A（推荐）：按历史录音文件平均大小统计 `avg_audio_mb_per_min`，则  
  `V_audio_gb_month = H_call_month * 60 * avg_audio_mb_per_min / 1024`
- 方法 B（简化）：抽样 N 天录音文件，取平均文件大小后用  
  `V_audio_gb_month = N_call_month * avg_audio_mb_per_call / 1024`

针对本项目链路，可能涉及的网络数据流包含：

- 云呼叫平台产生的录音文件：服务端拉取到你们的 ASR/OSS（通常是主要音频出入流来源）
- ASR 服务（本地/独立服务）下载录音：可能产生跨服务器/跨区域的流量
- OSS/S3 等存储：录音落库与 ASR 拉取之间的跨区域/跨网络费用（若存在）

### 12.5 综合分析建议（用“总拥有成本 TCO”做最终决策）

把三类成本加总即可得到呼叫侧“总拥有成本”：

`C_total_call = C_saas 或 C_hw + C_net_audio + 可能的运维成本（值班/维护）`

决策要点：

- 当月通话量 `H_call_month` 较高且峰值集中：云呼叫 SaaS 的“通道能力即开即用”通常更省运维，且可控性强
- 当月通话量持续高、且你们愿意承担设备维护：硬件话机往往在长期单位成本上更有优势
- 不论云呼叫还是硬件：尽量让“录音文件的存储与 ASR 推理在同地域/同网络”以降低 `P_egress` 的放大效应

## 13. 按销售总量（10~50人）进行“实际口径”费用测算样例（30天）

你给定的业务规则：

- 每个销售每天 `100` 个电话
- 每个电话平均 `5` 分钟
- 统计周期按 `30` 天/月

### 13.1 月度业务量换算（精确）

设销售人数为 `N_sales`：

- 月通话笔数：`N_call_month = N_sales * 100 * 30 = N_sales * 3000（次/月）`
- 月通话总时长（分钟）：`H_call_min_month = N_sales * 100 * 5 * 30 = N_sales * 15000（分钟/月）`
- 月通话总时长（小时）：`H_call_month_h = H_call_min_month / 60 = N_sales * 250（小时/月）`

对应 10~50 人（示例）：

| 销售人数 `N_sales` | 月通话笔数 `N_call_month`（次） | 月通话时长（小时） `H_call_month_h` | 月通话时长（分钟） `H_call_min_month` |
| -----------------: | ------------------------------: | ----------------------------------: | ------------------------------------: |
|                 10 |                          30,000 |                               2,500 |                               150,000 |
|                 20 |                          60,000 |                               5,000 |                               300,000 |
|                 30 |                          90,000 |                               7,500 |                               450,000 |
|                 40 |                         120,000 |                              10,000 |                               600,000 |
|                 50 |                         150,000 |                              12,500 |                               750,000 |

### 13.2 云端费用：通话 SaaS +（AI）Token 费用 + 网络（按经验）

#### 13.2.1 云呼叫平台（SaaS）费用

用你们厂商的口径填入：

- `C_saas = H_call_min_month * P_minute + N_channel * P_channel_month + C_setup_month + 其他`

其中：

- `P_minute`：云呼叫平台按分钟单价（元/分钟）
- `N_channel`：所需通道/并发外呼能力（个）

#### 13.2.2 云侧 Token 费用（示例：按 LLM/AI 调用折算）

说明：你在问题里提到“云调用 API 走 token，本地部署采用并部署模型”。你们当前后端 `AiService.chat()` 属于 token 计费模式，因此这里把“AI 处理通话转写/分析”的 token 费用单独测算。

为了能给出可用的测算结果，这里需要做“行业经验假设”，并明确它们是可替换的：

- `tokens_in_per_min`：每分钟转写文本对应的输入 token（经验值，可替换）
- `tokens_out_per_min_ratio`：输出 token 与输入 token 的比例（经验值，可替换，默认 `0.25`）
- `k_llm_calls_per_min`：单位分钟触发的 LLM 总调用倍率（例如主分析 1 次 + 可选补分析折算，经验值，可替换，默认 `1.3`）
- `P_in_1m`：云端输入 token 单价（元/1M tokens）
- `P_out_1m`：云端输出 token 单价（元/1M tokens）

测算公式：

- `Tokens_in_month = H_call_min_month * tokens_in_per_min * k_llm_calls_per_min`
- `Tokens_out_month = Tokens_in_month * tokens_out_per_min_ratio`
- `C_cloud_token = (Tokens_in_month/1e6)*P_in_1m + (Tokens_out_month/1e6)*P_out_1m`

#### 13.2.3 云端网络费用（音频出入流量）

网络只要你把“平均每分钟音频大小”统计出来就能算，仍然给可替换口径：

- `avg_audio_mb_per_min`：平均录音文件大小（MB/分钟）
- `P_egress`：公网/跨区域出流单价（元/GB）

测算：

- `V_audio_gb_month = H_call_min_month * avg_audio_mb_per_min / 1024`
- `C_net_audio = V_audio_gb_month * P_egress + 其他传输项`

### 13.3 本地部署费用：GPU/算力 + 电费 + 运维 + 网络（按经验）

这里给出两层费用核算：

#### 13.3.1 本地 ASR（SenseVoiceSmall）电费与 GPU 运行时长（基于官方吞吐）

SenseVoice 官方给出：`10s 音频约 70ms`，可估算实时因子 `RTF = 0.007`。

用它把“音频时长”换成“GPU 实际运行时间（墙上时间）”：

- `audio_hours = H_call_month_h`
- `RTF = 0.07s/10s`
- `audio_to_wall_ratio = 1/RTF ≈ 142.9`
- 取 GPU 利用率（排队/批处理/OSS拉取等导致无法满载）`u（默认 0.7，可替换）`

则：

- `GPU_runtime_hours = audio_hours / (142.9 * u)`

电费（给出可替换参数）：

- `P_gpu_kW`：GPU 服务器平均功耗（kW，默认 0.6~1.0）
- `price_elec`：电价（元/kWh）

电费变量成本：

- `C_elec = GPU_runtime_hours * P_gpu_kW * price_elec`

#### 13.3.2 本地固定成本（GPU 折旧/租赁 + 运维）

本地部署通常固定成本会主导费用，因此必须填入或按经验估算：

- `C_ops_month`：运维与值班（月）（元/月）

则本地（ASR 部分）：

- `C_local_asr = C_gpu_fixed_month + C_ops_month + C_elec + 可能的存储/日志成本`

> 注意：如果你们“本地并部署模型”还包括 LLM/Embedding（替代 DashScope），则需再补一块 `C_local_llm`（需要你们本地 LLM 的单卡吞吐或 GPU 规格与成本）。本节先把“本地 ASR（SenseVoiceSmall）”成本落地到可估算公式。

#### 13.3.3 本地网络费用

- `C_net_audio_local = V_audio_gb_month * P_egress_local + 其他传输项`
