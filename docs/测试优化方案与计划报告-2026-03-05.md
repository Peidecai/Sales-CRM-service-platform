# CRM Sales Platform 测试优化方案与计划报告

- 版本: v1.0
- 日期: 2026-03-05
- 适用范围: `@crm/server`、`@crm/web`、`e2e`
- 目标: 在不降低交付速度的前提下，提升测试覆盖率、稳定性、执行效率和问题定位速度

## 1. 当前测试基线（2026-03-05实测）

### 1.1 代码与测试结构

- Monorepo: `pnpm workspace`
- 后端: NestJS + Jest
- 前端: Vue3 + Vitest
- E2E: Playwright（Chromium）
- CI: `.github/workflows/ci.yml` 已包含 lint / server test / web build / e2e / docker validate

### 1.2 实测结果（本地）

- 后端单元测试:
  - 命令: `pnpm --filter @crm/server test --coverage --runInBand`
  - 结果: `12` suites, `163` tests, 全通过
  - 耗时: `19.433s`
- 前端单元测试:
  - 命令: `pnpm --filter @crm/web test`
  - 结果: `5` files, `71` tests, 全通过
  - 耗时: `1.91s`
- E2E:
  - 命令: `pnpm test:e2e`
  - 结果: `46` tests, 全通过
  - 耗时: `9.7s`

### 1.3 覆盖率现状

- 后端覆盖率（Jest）:
  - Statements: `57.99%`
  - Branches: `55.13%`
  - Functions: `45.99%`
  - Lines: `58.52%`
- 前端覆盖率（Vitest）:
  - 当前无法产出覆盖率，执行 `pnpm --filter @crm/web test:cov` 提示缺少依赖 `@vitest/coverage-v8`

### 1.4 主要短板

- 后端“横切层”覆盖率偏低（filter/interceptor/guard/redis/processor 等）
- 前端覆盖率体系未闭环（缺失 coverage provider）
- 端到端目前偏 UI 流程验证，缺少关键业务失败路径与数据一致性断言
- 失败诊断信息仍可增强（测试日志、失败工件分级、重试策略分层）

## 2. 优化目标（分层KPI）

## 2.1 质量目标（8周）

- 后端覆盖率提升到:
  - Statements/Lines `>= 70%`
  - Branches `>= 60%`
  - Functions `>= 60%`
- 前端建立覆盖率基线并达成:
  - Statements/Lines `>= 60%`
- E2E稳定性:
  - 主干分支（`main/develop`）最近30天 flaky rate `< 2%`

### 2.2 效率目标

- PR 快速回归（不含全量E2E）控制在 `<= 8 分钟`
- 全量质量门禁（含E2E）控制在 `<= 15 分钟`
- 失败后首轮定位时间（MTTD）下降 `30%`

## 3. 总体策略

### 3.1 测试分层重构

- L1 单元测试（毫秒级）
  - 关注纯函数、业务规则、边界与异常分支
- L2 模块集成测试（秒级）
  - 关注 service + repository/queue/cache 的协作
- L3 合同测试（接口契约）
  - 关键 API 请求/响应 schema 校验
- L4 E2E（分钟级）
  - 仅保留关键链路与高风险流程

### 3.2 测试执行分道

- PR 快速道:
  - server unit + web unit + type-check + changed-scope e2e smoke
- 合并前完整道:
  - 全量 unit + 全量 e2e + build + docker validate
- 夜间道:
  - 全量覆盖率 + 压力/稳定性 + flaky 探测

### 3.3 “稳定优先”原则

- 新增测试优先 mock 外部依赖（AI/Redis/网络）
- 禁止非确定性断言（时间、随机、异步竞争）
- 每个 flaky 用例必须有 owner、根因、修复截止日期

## 4. 分阶段落地计划

## 阶段A（2026-03-06 ~ 2026-03-12）：基线治理与门禁补齐

### 目标

- 建立统一质量基线与最小门禁，不改业务逻辑

### 任务

- 安装前端覆盖率依赖并打通报告
  - `@vitest/coverage-v8`
- 在 CI 增加前端覆盖率产物上传（与 server coverage 对齐）
- 增加统一测试入口脚本（建议）:
  - `test:quick`, `test:full`, `test:ci`
- 规范测试执行环境文档（Node/pnpm/Playwright/browser cache）

### 验收标准

- Web 覆盖率报告可稳定产出
- 本地与 CI 执行命令一致

## 阶段B（2026-03-13 ~ 2026-03-26）：覆盖率提升（后端优先）

### 目标

- 重点补齐低覆盖模块与风险路径

### 任务

- 后端优先补测模块:
  - `common/filters/http-exception.filter.ts`
  - `common/interceptors/*.ts`
  - `common/guards/roles.guard.ts`
  - `common/redis/redis.service.ts`
  - `modules/*/controller.ts` 关键分支
- 每个模块至少新增:
  - 正常路径
  - 权限/参数异常路径
  - 依赖失败降级路径

### 验收标准

- 后端覆盖率达到阶段目标:
  - Statements/Lines `>= 65%`
  - Branches `>= 58%`
  - Functions `>= 55%`

## 阶段C（2026-03-27 ~ 2026-04-09）：E2E提效与抗脆弱改造

### 目标

- 降低 flaky，提升问题定位效率

### 任务

- 将 E2E 分层:
  - smoke（核心链路）
  - regression（全量）
- 强化 Playwright 工件策略:
  - 失败自动保留 trace/video/screenshot
  - 用例命名规范化（业务动作 + 预期）
- 引入重试分层:
  - CI flaky only retry，不对本地默认重试
- 增加“数据断言”而非纯文本断言

### 验收标准

- E2E 最近两周 flaky rate `< 3%`
- 单次失败可在 `10 分钟`内定位到模块级原因

## 阶段D（2026-04-10 ~ 2026-04-24）：CI性能与治理闭环

### 目标

- 在保证质量门禁的同时，缩短等待时间

### 任务

- CI按路径变更触发差异任务（paths filter）
- Playwright 分片并行（shard）
- 覆盖率阈值逐步门禁化（先 warning 后 blocking）
- 周报化质量看板:
  - 通过率
  - 覆盖率趋势
  - flaky Top N
  - 平均耗时

### 验收标准

- PR 快速道 `<= 8 分钟`
- 完整道 `<= 15 分钟`
- 覆盖率达到总目标

## 5. 具体优化清单（按优先级）

### P0（立即执行）

- 补齐 `@vitest/coverage-v8` 依赖
- 增加 `test:quick/test:full/test:ci` 标准脚本
- 统一测试文档与命令入口

### P1（两周内）

- 后端低覆盖模块补测
- E2E smoke/regression 分层
- 失败工件与日志规范化

### P2（四周内）

- CI 路径增量触发
- E2E 分片并行
- 覆盖率阈值门禁逐步收紧

## 6. 推荐命令矩阵（团队统一）

### 本地开发（快速反馈）

- `pnpm --filter @crm/web test`
- `pnpm --filter @crm/server test --runInBand`
- `pnpm test:e2e -- --grep Dashboard --workers=1`

### 提交前（完整回归）

- `pnpm --filter @crm/server test --coverage --runInBand`
- `pnpm --filter @crm/web test`
- `pnpm test:e2e`
- `pnpm build`

### CI

- 保持现有 `ci.yml` 主流程
- 增补:
  - web coverage job/upload
  - e2e smoke 与 regression 分离
  - 失败自动生成摘要（可选）

## 7. 风险与应对

- 风险: 覆盖率门禁过早上线导致开发阻塞
  - 应对: 分阶段阈值，先 warning 再 fail
- 风险: E2E 并行度提升引发资源争抢
  - 应对: 固定 worker 上限 + shard 分片
- 风险: Mock 过多导致与真实行为偏差
  - 应对: 保留少量真实链路集成测试作为校验锚点

## 8. 资源与角色建议

- 测试负责人（1人）
  - 统筹方案推进、指标跟踪、review 质量
- 模块 owner（后端/前端各1-2人）
  - 负责本模块补测与缺陷闭环
- CI owner（1人）
  - 负责流水线效率与可观测性

## 9. 交付物清单

- 测试策略文档（本报告）
- 统一命令与执行手册
- 覆盖率看板（server + web）
- E2E 分层清单（smoke/regression）
- 每周质量周报模板

## 10. 结论

项目当前“可测性基础”较好（server/web/e2e均可稳定执行），但在覆盖率闭环、横切层补测和 CI 分层效率方面仍有明显提升空间。
建议按本计划分四阶段推进，优先做 P0/P1，预计在 4~8 周内可将质量稳定性和交付效率拉升到可持续状态。
