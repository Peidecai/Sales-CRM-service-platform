## 1. 系统总体设计

### 1.1 设计目标与原则

#### 1.1.1 设计目标

#### 一、功能目标

| 目标领域     | 具体目标                                                                  | 量化指标                     |
| ------------ | ------------------------------------------------------------------------- | ---------------------------- |
| 客户管理     | 实现客户全生命周期管理，涵盖线索获取、客户建档、跟进记录、商机转化全流程  | 支持百万级客户数据管理       |
| 销售流程     | 构建可视化、可配置的销售漏斗与流程引擎，支持从线索到回款的闭环管理        | 销售阶段转化率可追踪至每一步 |
| 呼叫中心     | 集成阿里云语音服务与讯飞ASR，实现一键外呼、通话录音、语音转文字、智能质检 | 支持50路并发通话             |
| AI智能分析   | 基于Claude API实现客户画像生成、成交概率预测、话术推荐、销售策略建议      | AI响应时间 < 5s              |
| 销售信息管理 | 产品库、价格体系、合同管理、业绩报表、团队协作等基础信息管理              | 报表生成时间 < 3s            |

#### 二、性能目标

| 性能指标          | 目标值  | 说明                 |
| ----------------- | ------- | -------------------- |
| API平均响应时间   | ≤ 200ms | 常规CRUD接口（P95）  |
| API峰值响应时间   | ≤ 500ms | 复杂查询接口（P99）  |
| 并发用户数        | ≥ 500   | 同时在线活跃用户     |
| QPS（每秒查询数） | ≥ 2000  | 单节点吞吐量         |
| 数据库查询耗时    | ≤ 50ms  | 单表查询（P95）      |
| 页面首屏加载时间  | ≤ 1.5s  | Gzip压缩 + CDN加速后 |
| WebSocket消息延迟 | ≤ 100ms | 实时通知推送         |

#### 三、可用性目标

| 可用性指标          | 目标值   | 说明                      |
| ------------------- | -------- | ------------------------- |
| 系统可用性（SLA）   | ≥ 99.9%  | 年度不可用时间 < 8.76小时 |
| RTO（恢复时间目标） | ≤ 30分钟 | 故障后恢复业务时间        |
| RPO（恢复点目标）   | ≤ 5分钟  | 数据最大丢失时间窗口      |
| 发布停机时间        | 0        | 蓝绿部署实现零停机发布    |
| 自动故障转移时间    | ≤ 30秒   | SLB健康检查触发自动切换   |

#### 1.1.2 设计原则

#### 一、SOLID原则在系统中的应用

| 原则             | 全称                            | 在本系统中的应用                                                                                                                                                                       |
| ---------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** - 单一职责 | Single Responsibility Principle | 每个NestJS Service仅负责单一业务领域。如 `CustomerService` 仅处理客户相关逻辑，`CallService` 仅处理呼叫相关逻辑。Controller仅负责请求路由与参数校验，不包含业务逻辑。                  |
| **O** - 开闭原则 | Open/Closed Principle           | 销售流程引擎通过策略模式（Strategy Pattern）实现阶段转换规则的扩展，新增销售阶段无需修改已有流转代码。AI分析模块通过适配器模式隔离Claude API，未来可替换为其他AI引擎而不影响上层业务。 |
| **L** - 里氏替换 | Liskov Substitution Principle   | 存储层定义统一的 `IStorageService` 接口，本地存储和阿里云OSS存储均实现该接口，可在不同环境透明替换。缓存层 `ICacheService` 支持Redis实现与内存缓存实现的无缝切换。                     |
| **I** - 接口隔离 | Interface Segregation Principle | 将大接口拆分为细粒度接口。如客户模块拆分为 `ICustomerQuery`（查询接口）、`ICustomerCommand`（命令接口）、`ICustomerExport`（导出接口），调用方仅依赖所需接口。                         |
| **D** - 依赖倒置 | Dependency Inversion Principle  | 领域层定义Repository接口（如 `ICustomerRepository`），基础设施层提供TypeORM实现。通过NestJS的依赖注入容器实现控制反转，高层模块不依赖低层模块的具体实现。                              |

#### 二、12-Factor App原则的应用

| 因子 | 名称                                 | 在本系统中的实践                                                                                          |
| ---- | ------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| I    | 基准代码 (Codebase)                  | 单一Git仓库（Monorepo），前端、后端、APP各为独立workspace，通过pnpm workspaces管理                        |
| II   | 依赖 (Dependencies)                  | 通过 `package.json` 显式声明全部依赖，不依赖系统级隐式包，使用 `pnpm-lock.yaml` 锁定版本                  |
| III  | 配置 (Config)                        | 环境变量管理全部配置（数据库连接串、API密钥、OSS配置等），通过 `.env` 文件注入，敏感配置使用阿里云KMS加密 |
| IV   | 后端服务 (Backing Services)          | MySQL、Redis、OSS、Claude API、讯飞ASR、阿里云语音服务均作为附加资源，通过配置绑定，可独立替换            |
| V    | 构建/发布/运行 (Build, Release, Run) | 严格分离三阶段：CI构建Docker镜像 → 打标签发布 → ECS容器运行，不允许运行时修改代码                         |
| VI   | 进程 (Processes)                     | 应用进程无状态化，会话状态存储于Redis，文件存储于OSS，支持随时销毁与重建                                  |
| VII  | 端口绑定 (Port Binding)              | NestJS通过HTTP端口自包含导出服务，不依赖外部应用服务器（如Apache/Nginx代理非必需）                        |
| VIII | 并发 (Concurrency)                   | 通过进程模型实现横向扩展，PM2 Cluster模式或Docker多实例部署，SLB负载均衡分发请求                          |
| IX   | 易处理 (Disposability)               | 快速启动（< 10s）与优雅终止（SIGTERM信号处理，完成进行中请求后退出），支持弹性伸缩                        |
| X    | 开发/生产等价 (Dev/Prod Parity)      | Docker Compose本地开发环境与生产环境保持技术栈一致，最小化环境差异                                        |
| XI   | 日志 (Logs)                          | 日志作为事件流输出至stdout，由日志收集器（阿里云SLS）统一采集、索引、分析                                 |
| XII  | 管理进程 (Admin Processes)           | 数据库迁移（TypeORM Migration）、数据初始化脚本作为一次性进程运行，纳入版本管理                           |

#### 1.4.2 各层详细说明

#### 一、表现层 (Presentation Layer)

| 组件                           | 说明                                       | 技术实现                                    |
| ------------------------------ | ------------------------------------------ | ------------------------------------------- |
| **Controllers**                | 定义HTTP/WebSocket端点，接收请求，返回响应 | `@Controller()`, `@Get()`, `@Post()` 装饰器 |
| **DTO (Data Transfer Object)** | 请求/响应数据结构定义与验证                | `class-validator` + `class-transformer`     |
| **Guards**                     | 请求拦截，认证鉴权                         | `@UseGuards(JwtAuthGuard, RolesGuard)`      |
| **Interceptors**               | 请求/响应拦截处理（日志、缓存、格式化）    | `@UseInterceptors(LoggingInterceptor)`      |
| **Pipes**                      | 参数转换与校验                             | `ValidationPipe`, `ParseIntPipe`            |
| **Filters**                    | 全局异常捕获与统一错误响应                 | `@Catch(HttpException)`                     |

**层内规则：**

- Controller不包含任何业务逻辑，仅做请求分发
- 所有入参必须通过DTO + ValidationPipe校验
- 响应数据必须通过ResponseDTO格式化，不直接返回领域实体

#### 二、应用层 (Application Layer)

| 组件                    | 说明                             | 技术实现                     |
| ----------------------- | -------------------------------- | ---------------------------- |
| **Application Service** | 用例编排，协调领域服务与基础设施 | NestJS Injectable Service    |
| **Command Handlers**    | 处理写操作命令（创建/更新/删除） | CQRS模式（可选@nestjs/cqrs） |
| **Query Handlers**      | 处理读操作查询                   | 独立查询路径，可优化读性能   |
| **Event Handlers**      | 处理领域事件的副作用逻辑         | EventEmitter2 / Bull Queue   |
| **DTO Mapping**         | DTO与领域模型之间的转换          | 手动映射或AutoMapper         |

**层内规则：**

- 应用服务是事务的边界，通过 `@Transaction()` 装饰器管理数据库事务
- 应用服务负责权限的业务校验（Guard已完成认证，此处做资源级授权）
- 一个用例对应一个Application Service方法
- 禁止在应用层编写领域业务规则

#### 三、领域层 (Domain Layer)

| 组件                     | 说明                                 | 技术实现                   |
| ------------------------ | ------------------------------------ | -------------------------- |
| **Entity**               | 具有唯一标识的领域对象，封装业务行为 | TypeScript类，包含业务方法 |
| **Value Object**         | 无标识的不可变对象，描述属性特征     | 不可变TypeScript类         |
| **Domain Service**       | 不属于单一实体的跨实体业务逻辑       | 纯TypeScript类，无框架依赖 |
| **Repository Interface** | 聚合根的持久化接口定义（仅接口）     | TypeScript Interface       |
| **Domain Event**         | 领域内发生的业务事件                 | 事件类定义                 |

**层内规则：**

- **领域层是架构的核心，不依赖任何外层和外部框架**
- 实体必须封装业务规则，外部不可直接修改实体状态（rich domain model）
- Repository仅定义接口，实现由基础设施层提供
- 值对象必须不可变（所有属性readonly）
- 领域事件用于解耦跨聚合的副作用

#### 四、基础设施层 (Infrastructure Layer)

| 组件                      | 说明                                    | 技术实现                                              |
| ------------------------- | --------------------------------------- | ----------------------------------------------------- |
| **TypeORM Repository**    | 领域Repository接口的具体实现            | TypeORM EntityRepository                              |
| **Redis Cache**           | ICacheService接口的Redis实现            | `@nestjs/cache-manager` + `cache-manager-redis-store` |
| **OSS Storage**           | IStorageService接口的阿里云OSS实现      | `ali-oss` SDK                                         |
| **External API Adapters** | Claude API、讯飞ASR、阿里云语音等适配器 | 适配器模式封装外部SDK                                 |
| **Config Module**         | 环境变量与配置管理                      | `@nestjs/config`                                      |
| **Queue Provider**        | Bull Queue的队列配置与Worker            | `@nestjs/bull`                                        |

**层内规则：**

- 通过依赖注入实现接口绑定：`{ provide: ICustomerRepository, useClass: CustomerTypeOrmRepository }`
- 外部API必须通过适配器模式封装，领域层不直接依赖外部SDK
- 数据库Entity（TypeORM Entity）与领域Entity分离，通过Mapper转换

#### 1.4.3 层间调用规则与约束

```
┌─────────────────────────────────────────────────────────────────────┐
│                       层间调用规则矩阵                               │
│                                                                     │
│              调用目标 →                                              │
│  调用源 ↓     表现层    应用层    领域层    基础设施层                  │
│  ─────────────────────────────────────────────────                   │
│  表现层        ─        允许      禁止      禁止                      │
│  应用层        禁止      ─        允许      允许(通过接口)              │
│  领域层        禁止      禁止      ─        禁止                      │

│                                                                     │
│  关键约束:                                                           │
│  1. 依赖方向: 外层 → 内层 (表现→应用→领域)                            │
│  2. 依赖倒置: 基础设施层实现领域层定义的接口                            │
│  3. 禁止跨层调用: 表现层不可直接调用领域层或基础设施层                   │

```

┌──────────────────────────────────────────────────────────────────────────────┐

│                                                                              │

│    │ ◀──────────────────────────│                              │             │
│    │                            │                              │             │
│    │  4. POST /auth/refresh     │                              │             │

│    │                            │──────────────────────────────▶│             │

│    │                            │◀──────────────────────────────│             │

│    │   newRefreshToken}         │  更新 Redis 中的 RT           │             │
│    │ ◀──────────────────────────│                              │             │
│    │                            │                              │             │

│    │ ◀──────────────────────────│                              │             │
│                                                                              │
│  Token配置:                                                                  │
│  ┌───────────────────┬──────────────────────────────────┐                    │
│  │ Access Token (AT) │ 有效期: 15分钟                     │                    │
│  │                   │ 载荷: userId, roles, permissions  │                    │

#### 1.6.2 日志体系 — Winston日志分级

| 日志级别    | 用途                 | 示例场景                                      | 持久化策略                      |
| ----------- | -------------------- | --------------------------------------------- | ------------------------------- |
| **error**   | 系统错误，需立即关注 | 数据库连接失败、外部API异常、未捕获异常       | 写入文件 + 阿里云SLS + 告警通知 |
| **warn**    | 警告信息，潜在问题   | 接口响应慢（>1s）、缓存未命中率过高、重试操作 | 写入文件 + 阿里云SLS            |
| **info**    | 关键业务流程日志     | 用户登录/登出、客户创建/更新、订单状态变更    | 写入文件 + 阿里云SLS            |
| **debug**   | 调试信息             | SQL查询语句、请求/响应详细数据、变量状态      | 仅开发环境写入文件              |
| **verbose** | 详细追踪信息         | 函数调用链路、中间计算结果                    | 仅开发环境控制台输出            |

**日志格式规范：**

```
{
  "timestamp": "2026-03-03T10:30:00.000Z",
  "level": "info",
  "traceId": "abc-123-def-456",           // 请求链路追踪ID
  "userId": 1001,                          // 操作用户ID
  "module": "CustomerModule",             // 业务模块
  "action": "createCustomer",            // 操作动作
  "message": "Customer created successfully",
  "metadata": {
    "customerId": 5001,
    "customerName": "XX科技有限公司",
    "duration": 45                         // 操作耗时(ms)
  },
  "request": {
    "method": "POST",
    "url": "/api/customers",
    "ip": "192.168.1.100",
    "userAgent": "Mozilla/5.0..."
  }
}
```

**日志实现要点：**

- 全局 `LoggingInterceptor` 自动记录每个请求的入参、出参、耗时
- 通过 `cls-hooked` 实现 traceId 在异步调用链中的自动传递
- 敏感字段（密码、Token、身份证号）自动脱敏处理
- 日志文件按天轮转（daily rotate），保留30天，单文件上限50MB

#### 1.7.3 安全性需求

| 安全领域     | 安全措施                    | 实现方式                                           |
| ------------ | --------------------------- | -------------------------------------------------- |
| **传输安全** | 全链路HTTPS加密             | SLB SSL卸载 + TLS 1.2+ + HSTS Header               |
| **认证安全** | JWT双Token + 密码加密存储   | RS256非对称签名 + bcrypt密码哈希（salt rounds=12） |
| **授权安全** | RBAC + 数据权限             | 角色-权限矩阵 + 行级数据过滤（本人/部门/全公司）   |
| **输入安全** | 参数校验 + SQL注入防护      | class-validator + TypeORM参数化查询（杜绝SQL拼接） |
| **XSS防护**  | 输出编码 + CSP策略          | Vue 3自动HTML转义 + Content-Security-Policy Header |
| **CSRF防护** | SameSite Cookie + Token验证 | SameSite=Strict + 自定义X-CSRF-Token Header        |
| **接口安全** | 频率限制 + IP黑名单         | @nestjs/throttler（100次/分钟） + IP白名单         |
| **数据安全** | 敏感数据加密存储            | AES-256加密手机号/身份证 + 日志脱敏                |
| **审计安全** | 全操作审计日志              | 操作日志表记录：操作人、操作时间、操作内容、IP地址 |
| **依赖安全** | 依赖漏洞扫描                | npm audit + Snyk定期扫描 + Dependabot自动更新      |

#### 1.7.5 可维护性设计

| 维护领域       | 设计策略         | 具体措施                                                                      |
| -------------- | ---------------- | ----------------------------------------------------------------------------- |
| **代码规范**   | 统一编码标准     | ESLint + Prettier + Husky pre-commit钩子强制执行；TypeScript strict模式       |
| **API文档**    | 自动化文档生成   | @nestjs/swagger自动生成OpenAPI 3.0文档，代码即文档，文档随代码实时更新        |
| **数据库迁移** | 版本化Schema管理 | TypeORM Migration脚本纳入Git版本管理，支持升级/回滚；禁止手动修改生产库表结构 |
| **自动化测试** | 多层次测试策略   | 单元测试（Jest，覆盖率 > 80%）+ 集成测试（Supertest） + E2E测试（Cypress）    |
| **CI/CD**      | 全自动化流水线   | GitHub Actions / 阿里云效：代码检查 → 测试 → 构建 → 部署（蓝绿发布）          |
| **监控告警**   | 全方位可观测性   | 阿里云ARMS（应用监控）+ SLS（日志分析）+ CloudMonitor（基础设施监控）         |
| **错误追踪**   | 实时错误感知     | 全局异常捕获 + traceId链路追踪 + 告警通知（钉钉/邮件/短信）                   |
| **配置管理**   | 环境隔离         | .env环境变量 + 阿里云ACM配置中心；敏感配置KMS加密                             |
| **依赖管理**   | 安全更新机制     | pnpm-lock.yaml锁定版本 + Dependabot自动依赖更新PR + npm audit安全审计         |
| **技术债务**   | 持续改进         | SonarQube代码质量分析 + 技术债务看板 + 定期重构Sprint                         |
